run solutions, recover secrets, or test payloads.

from the sanitized catalog plus static inspection of framework, target, Docker, and
Kubernetes source. It is distinct from the separately gated Codex Security product
and from the API-backed workflow used for repeatable future runs. Risk ratings describe
the production impact of the represented weakness, not whether a deliberately vulnerable

The strongest existing controls are the external ranges' pinned revisions, internal
Docker networks with a narrow read-only TCP gateway, loopback publication by default,
the Kubernetes default-deny baseline, canary rather than production secrets, and the
strict separation between model generation and repository publishing in the workflow.

Across the challenge portfolio, the most reusable engineering rule is to enforce
identity, object, action, purpose, and destination at the service that owns each effect.
Model instructions, prompt filters, tool descriptions, and user approvals are supporting
signals; they cannot replace deterministic authorization, least privilege, isolation,
and end-to-end audit correlation.

## How to use these models

1. Confirm the listed assets, identities, protocols, and trust boundaries against the intended deployment.
2. Implement the **Secure before abuse** controls at the service that owns each effect or data object.
3. Add the benign negative tests under **Safe defensive validation** to the normal engineering test suite.
4. Route the monitoring signals to an owner and rehearse the response before exposing the system.
5. Record accepted residual risks and rerun the workflow after architecture or catalog changes.
