# RedSec control-gap matrix

This is the short-form view of the full [Codex threat-model portfolio](OVERVIEW.md).
It answers five questions for each major component: what it is, what can go wrong,
who can cause it, which controls RedSec currently implements, and which controls are
still missing.

“Controls in place” means a control is supported by repository evidence. Many target
applications deliberately omit the production control because demonstrating that gap
is the lesson. A deployment control marked **path-dependent** applies only on the run
paths named in the cell. Controls inside the four external projects are **not
verified—outside the current scope** because their pinned source is not stored in this
repository.

| Component | Threat | Who can exploit it | Controls in place | Controls missing |
|---|---|---|---|---|
| Public target exposure | An internet or LAN user reaches deliberately vulnerable services. | Any network user who can reach a published port. | Docker ports bind to loopback by default; Codespaces forwarding is private; Kubernetes uses `ClusterIP`; Fly defines no public service. | Reject non-loopback publication in managed environments; require an explicit unsafe override for `REDSEC_BIND_HOST=all`; continuously assert that no public ingress exists. |
| Agent prompt and context assembly | Direct, indirect, or encoded instructions override intended policy and steer disclosures or tools. | A user, document author, retrieved-content contributor, tool server, or compromised upstream agent. | Training data and secrets are synthetic; targets are separated from the control CLI; the deterministic mock makes behavior reproducible. No production prompt defense is claimed. | Preserve provenance for every context segment; separate instructions from data; keep secrets out of context; enforce disclosure and effect policy in deterministic application code. |
| Agent memory | Poisoned instructions persist across turns, cross users, or expose retained credentials. | A user or content source allowed to create memory; a compromised agent with memory-write access. | State is confined to the training target and can be reset; only planted data should be used. | Partition by tenant, user, agent, and purpose; authorize every read/write; record provenance; add review, expiry, revocation, and incident-wide purge. |
| A2A identities, messages, tasks, and context | A forged peer, replayed message, or smuggled context gains transitive authority. | A malicious peer agent, compromised trusted agent, or caller able to supply A2A metadata. | The A2A target uses synthetic identities and state inside a module boundary. | Cryptographically bind Agent Cards and keys; sign messages; validate issuer, audience, sender, recipient, task, context, nonce, and expiry; propagate attenuated originating authority. |
| RAG ingestion and retrieval | Poisoned content dominates retrieval or a forged citation makes untrusted material appear authoritative. | A document contributor, compromised source, or tenant probing shared retrieval. | The built-in corpus is synthetic and confined to its training target. | Authorize ingestion; retain immutable source provenance; enforce tenant filters before retrieval; add ranking-diversity and poisoning checks; render citations only from verified server-side identifiers. |
| Embedding and vector services | Adaptive queries reveal source membership or content; collisions bypass a text-layer check. | An authenticated query client or tenant with repeated vector-search access. | Built-in records are planted training data inside an isolated module. | Restrict vector and source access by tenant and purpose; limit score precision and adaptive queries; add privacy testing; never use semantic similarity as an authorization decision. |
| MCP tool registry and metadata | Tool poisoning, shadowing, typosquatting, or a rug pull acquires a trusted tool identity. | A malicious MCP server, registry publisher, compromised package, or intermediary. | External source revisions are commit-pinned; MCP host and server are separate targets; deployment boundaries limit some blast radius. | Bind approval to signed publisher identity plus an immutable tool digest; qualify names by server; reject ambiguous routing; require reapproval whenever description, schema, endpoint, or behavior changes. |
| MCP tool execution and delegation | A model or server uses ambient authority to perform an action the originating user could not authorize. | A prompt attacker, malicious tool server, compromised host, or low-privilege user invoking a deputy. | Target relationships and egress intent are declared in manifests; Kubernetes provides a namespace boundary. Enforcement varies by run path. | Re-authorize every object and effect at the owning service; propagate the originating principal; issue one narrow credential per tool; constrain destinations; require bound approval for high-impact actions. |
| MCP transport, routing, and sessions | Parser disagreement, origin confusion, routing desynchronization, replay, or predictable sessions reaches a different method or user context. | A remote MCP client, malicious browser origin, network intermediary, or adjacent tenant. | Ports are loopback-bound by default; external gateways forward only catalogued ports. | Parse once into a canonical request used by both authorization and dispatch; validate origin and audience; bind headers, body, peer, method, and tool; use random expiring replay-safe session identifiers. |
| Filesystem, command, query, template, XML, and object parsers | Untrusted tool arguments escape their data context and read files, alter queries, or execute code. | A direct API caller or prompt-influenced agent controlling a tool argument or artifact. | Dangerous targets are explicitly marked; security documentation requires isolated use; Kubernetes supplies namespace-level containment when policy is enforced. | Replace interpreters with fixed or parameterized APIs; use safe serialization; canonicalize descriptor-relative paths; run non-root with read-only filesystems, default seccomp, dropped capabilities, and no unnecessary egress. |
| Server-side fetch and metadata access | A caller redirects a server fetcher to cloud metadata or internal services and steals workload authority. | An API user or agent that controls a URL, redirect, host, or remote content source. | Kubernetes has a default-deny policy when the CNI enforces it; external ranges use internal Docker networks unless egress is explicitly enabled. | Add scheme/host/port/path allowlists; reject private, loopback, link-local, and metadata destinations after resolution and on every redirect; block undeclared egress on built-in Docker and bare-local paths. |
| Service authentication and authorization | Unauthenticated administration, IDOR, excessive scope, or audience confusion exposes another object or privileged action. | An unauthenticated caller, low-privilege tenant, compromised agent, or confused deputy. | Network reachability is private by default; the challenge services use planted data. The vulnerable targets intentionally omit the relevant production checks. | Authenticate every service call; authorize subject, tenant, object, action, purpose, audience, and current state at the resource owner; use short-lived attenuated capabilities. |
| Secrets, provider credentials, logs, completions, and model metadata | Credentials or personal data leak through context, errors, debug logs, completions, artifacts, or tools. | A user, prompt attacker, malicious tool, target compromise, or operator with excessive log access. | The course uses canaries; keys are read from environment or managed secrets and are excluded from Git; reports and model requests are sanitized. | Keep provider keys outside vulnerable target containers; use a scoped inference broker; minimize response fields; redact telemetry; rotate short-lived audience-bound credentials; deploy canary detection. |
| Model, dataset, adapter, and package supply chain | An unsigned, poisoned, unsafe, or ambiguously resolved artifact changes behavior or executes during load/build. | A package publisher, model or data supplier, compromised maintainer, registry attacker, or dependency-confusion actor. | External repositories are pinned to full Git commits and updated individually; builds occur in separate images. | Pin base images and dependencies by digest; verify signatures and provenance; generate SBOMs; use non-executable model formats; inspect artifacts in a secret-free sandbox; gate promotion on behavior and lineage review. |
| Built-in Docker containment | A compromised target reaches the internet, another undeclared target, the Docker host, or a provider credential. | Anyone who solves an execution or SSRF challenge, or malicious content processed by a target. | Ports bind to loopback and containers use one Docker network per module. | The controller must enforce manifest `egress` and `allow_targets`; use internal/per-target networks, narrow gateways, capability drops, read-only filesystems, and benign tests proving denied edges stay denied. |
| Kubernetes containment | A compromised pod moves laterally, uses a service-account token, or escapes a weak privileged-target boundary. | A challenge participant who gains code execution inside a target pod. | Default-deny policy, namespace-per-module, `ClusterIP`, non-root identity, default seccomp, and dropped capabilities apply to ordinary targets. These controls require a policy-enforcing CNI. | Generate peer rules from `allow_targets`; test CNI enforcement; disable service-account token mounting; apply non-root, no-new-privileges, seccomp, and capability drops to execution labs as well. |
| External range containers and gateway | Third-party vulnerable code reaches the host or network, or a mutable upstream build changes the risk. | A challenge participant, compromised upstream source, or malicious dependency. | Full source-commit pins; one container and internal network per range; loopback-only read-only TCP gateway; outbound access is opt-in; updates are per range. | Pin base images; produce provenance and SBOMs; scan and review each update in a disposable builder; verify upstream application controls and add protocol-level adapter tests. |
| Drop sink and challenge verifier | A learner posts the expected marker directly and receives credit without exercising the intended path. | Any learner or compromised target able to reach the module sink. | Events are in-memory, bounded, contain only planted lab data, and are confined to the range. The documentation labels this a teaching oracle. | Authenticate events with per-run, per-target evidence credentials; bind challenge, source, path, and nonce; prevent direct learner access in graded deployments; protect event reads. |
| Repository-aware model assessment | Untrusted catalog text injects the reviewer, sensitive material reaches a model, or model output writes directly to the repository. | A malicious metadata contributor, compromised dependency, or faulty model response. | Sanitized inventory excludes flags, hints, solutions, target source, and credentials; model calls have no tools and use `store: false`; strict schema validation and blocked-content checks run before a separate publisher job. | Configure the protected `codex-threat-models` environment and credential; prefer workload identity federation; require human review and branch protection; connect Codex Security only when separately authorized. |
